# Логи взаимодействия в Telegram-группу

Связанные документы: `../MVP_BOT_SPEC.md` (§13), `../../../bot/README.md`, модуль `bot/src/interaction_log.py`.

## Зачем

На этапе MVP бот работает в **личке** с организатором и участниками. Чтобы команда видела качество парсинга и навигации **без тяжёлой аналитики** (JSONL, дашборды), в приватную Telegram-группу уходят два типа сообщений:

1. **Parser Quality Log** — сразу после каждого разбора текста брифа.
2. **Session Summary** — сжатый таймлайн сессии в конце диалога или на ключевых этапах.

Это инструмент **исследования и контроля качества** (парсер, пробелы в брифе, типичные шаги пользователя), а не продуктовая фича для конечных пользователей.

## Что не логируется

- Сообщения в групповых чатах поездки (MVP их не ведёт).
- Поле `context_raw` в JSON snapshot (намеренно исключается).
- Отдельные метрики в файлы / внешние системы — только Telegram-группа.

## Формат 1 — Parser Quality Log

**Когда:** сразу после парсинга текста организатора или участника (в т.ч. recovery-пути).

**Содержимое:**

| Блок | Описание |
|------|----------|
| User, role, событие | `chat_id`, имя, `@username`, роль, номер события |
| Step, parser | Шаг сценария и режим парсера |
| USER INPUT | Полный текст сообщения пользователя |
| PARSED BRIEF | Тот же HTML, что видит пользователь в чате |
| MISSING AFTER PARSE | Список полей из `missing_brief_fields` |
| MERGED EVENT BRIEF | JSON snapshot объединённого брифа (без `context_raw`) |

**Режим парсера (`parser`):**

- `rules_only` — только rule-based парсер;
- `llm+rules` — LLM + правила (`USE_LLM_BRIEF_PARSER=true`);
- `llm_fallback` — LLM недоступен, откат на rules.

Длинные отчёты режутся на части (лимит Telegram ~4000 символов на сообщение).

## Формат 2 — Session Summary

**Когда:**

- пауза без действий **~5 минут** (настраивается);
- этап **приглашения участников** (`invite_shown`);
- **подтверждение вклада участником** (`participant_confirmed`).

**Содержимое:** пользователь, роль, событие, длительность сессии, число действий, число шагов с парсингом, причина завершения, **ACTION TIMELINE** (время → действие на русском: `/start`, «мои события», показ invite и т.д.).

## Включение

### 1. Группа в Telegram

1. Создайте **приватную** группу (только команда).
2. Добавьте бота с правом **отправлять сообщения**.
3. Узнайте `chat_id` группы (отрицательное число), например:
   - переслать сообщение из группы в @RawDataBot;
   - `getUpdates` Bot API после сообщения в группу;
   - локальный запуск бота и просмотр `chat.id` в логах.

**Не коммитить** `chat_id` в репозиторий — только Variables в Railway / локальный `.env`.

### 2. Переменные окружения

| Переменная | Пример | Назначение |
|------------|--------|------------|
| `LOG_GROUP_ENABLED` | `true` | Включить отправку (`1`, `true`, `yes`) |
| `LOG_GROUP_CHAT_ID` | `-5034705650` | ID группы |
| `LOG_SESSION_IDLE_SEC` | `300` | Пауза до Session Summary (мин. 60 с) |

Шаблон: `bot/.env.example`.

### 3. Деплой

Код логов в образе Railway — ветка `main`, модуль `bot/src/interaction_log.py`. После изменения Variables — **Redeploy** или автодеплой с GitHub.

Проверка: `/start` → создать событие → отправить текст брифа → в группе должен появиться **Parser Quality Log**.

## Безопасность и приватность

- Группа **только для внутренней команды**; в логах — реальные тексты брифов пользователей.
- Ошибка отправки лога **не блокирует** сценарий бота (warning в логах приложения).
- Не запускайте **два инстанса** одного бота (локально + Railway) — возможен `TelegramConflictError`.

## Диагностика

| Симптом | Что проверить |
|---------|----------------|
| Логов нет | `LOG_GROUP_ENABLED=true`, корректный `LOG_GROUP_CHAT_ID`, бот в группе, право писать |
| Логов нет после деплоя | В GitHub есть `interaction_log.py`; Railway пересобрался с последнего `main` |
| Только парсинг, нет Summary | Дождаться idle или дойти до invite / подтверждения участника |
| В Railway Deploy Logs | `Failed to send parse log to group` — права бота, неверный chat_id |

## Связь с исследованиями

Логи помогают при **решенческих и проблемных интервью**: сверять, что пользователь имел в виду в свободном тексте, с тем, что бот извлёк в бриф и что осталось в missing. См. также `Интервью_и_исследования.md`, `Решенческое_интервью.md`.

## Техническая реализация (кратко)

- Модуль: `bot/src/interaction_log.py`
- Вызовы из `bot/src/main.py`: `log_parse_result`, `log_session_action`, `flush_session_milestone`
- HTML для брифа — те же функции форматирования, что для пользователя (`format_brief_update_message` / `format_brief_for_participant`)
